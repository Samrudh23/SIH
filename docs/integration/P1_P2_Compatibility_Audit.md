## 1. Executive Summary

This compatibility audit validates that the data structures generated by the P1 extraction pipeline (`p1_extractor.py` / OCR / Vision models) correctly map to the input requirements of the P2 `RealComplianceEngine` via the P3 `ExtractionPayload` schema.

The primary requirement of this integration boundary is **zero loss of legal meaning**:
1. P1 must never make statutory determinations; it emits structural observations.
2. P3 must never discard multi-surface observations or silently collapse conflicts.
3. P2 evaluates the statutory rules and produces one of the 6 authoritative result states (`COMPLIANT`, `POTENTIAL_VIOLATION`, `NEEDS_MANUAL_REVIEW`, `NOT_APPLICABLE`, `NOT_DETECTED`, `ANALYSIS_FAILED`).
4. Dual confidence semantics (`detection_confidence` and `applicability_confidence`) are kept permanently distinct.
5. Incomplete package coverage generates `NEEDS_MANUAL_REVIEW`, never false violations.
6. The Fix 2 Medical Device Confirmation Gate is strictly enforced: `None` (pending), `False` (rejected), and `True` (confirmed).

## 3. Core Contract Requirements & Invariants

### 3.1 Multi-Surface Observation & Conflict Preservation
- **Problem**: When a package displays differing prices (e.g. ₹100 on front, ₹120 on back) or differing quantities (e.g. 500g on front, 400g on back), naive systems discard one reading.
- **Rule**: `ExtractionPayload.sync_observations` populates both `mrp_observations` and `net_quantity_observations`.
- **P2 Evaluation**: `RealComplianceEngine._detect_mrp_conflicts` and `_detect_net_quantity_conflicts` inspect all observations across submitted surfaces. Disagreements route to `NEEDS_MANUAL_REVIEW` with full conflict provenance (`values_found`, `image_id`, `location`).

### 3.2 Dual Confidence Semantics
- In every `RuleResult`, `detection_confidence` and `applicability_confidence` remain permanently separate.
- Neither confidence score is ever presented as "% legally compliant".
- If `detection_confidence < 0.75` for tax-inclusivity phrases on REQ-MVP-02, the result de-escalates to `NEEDS_MANUAL_REVIEW` (Fix 1).

### 3.3 Medical Device Confirmation Gate (Fix 2)
- Statutory routing under G.S.R. 778(E) excludes medical devices from standard PCR 2011 declarations.
- Automated bypass is strictly prohibited.
- Three-state workflow:
  - `is_medical_device_confirmed = None`: REQ-MVP-11 produces `NEEDS_MANUAL_REVIEW`.
  - `is_medical_device_confirmed = False`: Inspector rejects classification; standard PCR rules are applied.
  - `is_medical_device_confirmed = True`: Inspector confirms classification; standard PCR rules are marked `NOT_APPLICABLE`.

### 3.4 Image-Coverage-Aware Missing Declaration Handling
- If a declaration is missing from visible images:
  - If `image_coverage` for relevant surfaces is incomplete -> `NEEDS_MANUAL_REVIEW` ("Submitted images may not show this declaration — upload additional surfaces").
  - If `image_coverage` is complete -> `POTENTIAL_VIOLATION`.

### 3.5 Visual-Aid-Only Rule Constraints
- REQ-MVP-14 (Quiet Zone clearance) and REQ-MVP-15 (Contrast ratio) are qualitative visual aids.
- Under statutory principles, they **never** produce `COMPLIANT` or `POTENTIAL_VIOLATION`. They are schema-restricted to `NEEDS_MANUAL_REVIEW` or `NOT_DETECTED`.
